## 零、取用规则

1. **背景事实 ≠ 故事**。“唯一的 Android 工程师”“十年经验”“平安近六年”“每天约 30 万次规划任务”是背景事实：一场里交代一次，后面需要时用半句带过，不展开。
2. **一张卡一场最多完整讲一次**。完整 = 讲了矛盾 → 行动 → 结果。
3. **第二次用到同一张卡**：问的能力不同，**并且**能讲卡上另一个“侧面”（不同的矛盾、行动或结果），才能再讲；否则一句话带过（“就是我前面说的可之那次”），然后换一张卡。只换能力标签，不算换侧面。
4. **篇幅三档**：一句提及（自我介绍、动机类问题）/ 30 秒（追问、行为题的一部分）/ 1 分钟（主场题）。
5. **不需要故事的题**：自我介绍、职业动机、工作与生活平衡、为什么换行业、薪资、地点、到岗、利益冲突。用一句事实或观点回答，最多一句提及。
6. **按状态说话**：已上线的讲结果；开发中的只讲在做什么；设想只讲想法。Cabinet 不讲业务成效。
7. **数字只在主场讲**：SKU 300ms、首屏 3 秒 → 不到 1 秒、30 万次/天，各自只在主场题完整说一次。

## 一、卡片

### C01 可之：一个人四周把 Android App 从零做到上线
- **事实**：可之（2023.09–2025.02），App 工程团队有 Android 1 人、iOS 1 人、Web 3 人，向 CTO 汇报。我是唯一的 Android 工程师，四周内独立把 Android App 从零做到上线，同时负责测试和发布。当时（2023 年底）AI 编程工具还弱，代码基本手写。架构用 Jetpack + MVVM + DRouter 模块化，支持原生页面和内嵌 Web 页面，所以原生和 Web 功能都能赶进第一版。后端、Web、iOS 是别人做的。
- **状态**：已上线
- **最能证明**：紧迫期限下的交付和取舍
- **主场题**：F30 / H04（要快速推进）、F34（选简单方案提早上线）、B09（7H 的 Hustle）
- **侧面**：
  - 开发：先搭模块化 + Web 承载，让原生和 Web 功能都能进第一版（结构换速度）。
  - 研发交付：一个人包开发、测试、发布。→ 留给 N23（没有 QA，你能自己负责吗？）
  - 产品 / 创业（11-14 确认）：为了四周上线，第一版删掉了分享功能（不是核心），是和 CTO 当场拍板定的。→ 留给 F34（选简单方案提早上线）、“优先级怎么定”
- **一句话版**：At Kezhi, I was the only Android engineer, and I built the app from zero to launch in four weeks.
- **不能说**：后端 / iOS / Web 是我做的；用了 AI 编程工具。

### C02 可之：按科目、年级、章节检索的 RAG 问答
- **事实**：和 Android 并行负责（不是先后）。按科目、年级、章节、知识点建索引，向量检索 + BM25 关键词检索，再加元数据过滤；比喻成“开卷考试”：先找到对的材料，再让 AI 作答。这是我 AI 工作的起点，后来把 RAG 经验带到了 KKday。
- **状态**：已上线（作业批改产品第一版上线）
- **最能证明**：学新技术并做进产品；向非技术的人讲清楚技术
- **主场题**：N09（从 Android 转 RAG 了吗）、N31 / X22（用简单英语讲技术）、F47（最近学到的难东西，二选一）
- **侧面**：开发：混合检索怎么让答案准；产品：答案贴合学生的教材章节；创业：一个人横跨 App 和 AI 两块。
- **一句话版**：At Kezhi, I also built the RAG Q&A system at the same time as the Android app.

### C03 可之：批改产品没达到预期（复盘）
- **事实**：AI 批改作业的第一版已上线，几秒能批完一份作业，但还不能对每个学生的历史错题做足够的分类、总结和分析，不够支撑针对性教学。我负责的是 Android 和 RAG，不负责批改算法。错题记录、知识点归类、薄弱点总结都是复盘时的改进想法，不是已经做完的功能。没有测量过的分数提升。
- **状态**：第一版已上线；改进只是想法
- **最能证明**：反思、对用户价值的理解
- **主场题**：F29（项目没达到预期）、“回头看会怎么做”

### C04 KKday：AI 行程规划（技术负责人）
- **事实**：5 人项目，我是技术负责人：设计 agent 架构，接订单和商品工具，写核心后端，搭个性化数据层。和 App 团队一起定逐日行程卡、商品卡、地图点的返回格式，用 SSE 流式返回，第一张卡先出来。后端检查结构、商品 ID、地点限制，失败时带着具体错误重试，超过次数就回退到安全的默认结果。每天约 30 万次规划任务（含首次规划和修改）。没有转化率数据。
- **状态**：已上线（裁员后项目继续）
- **最能证明**：AI 产品落地、端到端负责
- **主场题**：F26（从模糊问题到交付）、F09（为什么选你而不是 AI 经验更新的人）、F24（agent/RAG 怎么改变你做移动端）
- **侧面**（每个侧面都是独立的内容，可以分给不同的题）：
  - 体验（产品）：先给用户看 Day 1，不用等整份计划。→ 等待与流式体验
  - 可靠性（研发）：结构校验 + 带错误重试 + 安全回退。→ AI 出错怎么办（F51、N20）
  - 架构（开发）：agent 和工具、个性化数据层。→ 技术深度
  - 规模（背景）：30 万次/天。→ 只当背景半句
- **不能说**：转化率提升；用户反馈说好。

### C05 KKday：SKU 选项切换 1 秒 → 300 毫秒
- **事实**：我亲手做的。日期 × 套餐 × 票种 × 加购互相依赖，每次点击都在主线程重算全部库存和价格，还反复解析 JSON。做法：拆平配置，提前建“组合 → 价格/库存”索引，计算移到 Dispatchers.Default，用 StateFlow 发结果，内存缓存。约 1 秒降到 300 毫秒。没有用户投诉或转化数据作为背景。
- **状态**：已上线
- **最能证明**：亲手做的性能优化
- **主场题**：F27（最自豪的成就）、N14（最能代表你的 Android 项目）、SKU 追问。每场只讲一次（已改）。
- **一句话版**：I also fixed the lag when users switched product options.

### C06 KKday：首屏 3 秒 → 不到 1 秒；引入 Compose
- **事实**：多级缓存（网络、本地、图片）+ 骨架屏（骨架屏让等待感觉更短，不减少真实加载时间）。首屏约 3 秒降到 1 秒以内，测量方式没记录。我把 Jetpack Compose 引入项目，页面全部用 Compose 重构，代码是 Kotlin；我在重构中占多少份额没确认。
- **状态**：已上线
- **最能证明**：用户体验 + 性能；现代 Android 技术栈
- **主场题**：B02（Why ActAI 里一句）、S02（empathetic 的例子：骨架屏）、N13（Compose）
- **注意**：不和 SKU 的数字混用。

### C07 KKday：后端改接口没通知 → 约定先发示例数据
- **事实**：订票页，后端改了库存状态的返回方式，没告诉 Android，导致有些有库存的套餐选不了。我对比实际返回和约定格式找到改动，和后端一起修，重测所有受影响的套餐。之后约定：共享接口改动先说明、先发示例数据。另一次是自己的计划问题：把接口问题留到最后一天，联调时发现缺货数据对不上，从此开工前先要示例数据（正常、有库存、缺货）。
- **状态**：已发生（两件不同的事）
- **最能证明**：跨端协作、把问题变成规则
- **主场题**：B04（不喜欢的工作方式）——只讲第一件；X02 / F35（错过期限 / 犯错）——只讲第二件
- **建议**：F42（异步沟通）、F43（跨时区）、F45（每周复盘）、F49 不再用它，改用 C08 或观点作答。

### C08 KKday：一个 Slack 频道 + 一份 Confluence 文档；技术分享会
- **事实**：我入职后提出的。之前文档分散，要一个个去问，容易遗漏。做法：每个项目一个 Slack 频道（RD、UED、PM Owner 都在），一份统一的 Confluence 文档（需求、设计、各端方案、QA 用例）。先在自己团队用，后来在我组织的每月技术分享会上介绍，推广到其他团队。没有统计过效果：只说“改动简单，效果明显”，功劳是“提出并推动”。
- **状态**：已落地
- **最能证明**：不靠职权推动改变；贡献不止写代码；远程 / 异步协作
- **主场题**：F28（职责外解决问题）、X12（无职权推动变化）、F42（异步沟通）、F43（跨时区）、X23（远程小团队文化）
- **侧面**：研发：接口先行、mock 先开发；产品：PM 决定变更带本版还是下一版；创业：写下来、可追溯，适合远程团队。
- **不能说**：返工减少多少（没统计）；“我改变了整个团队”。

### C11 德邦：边发版边做渐进模块化 / MVVM，培训团队
