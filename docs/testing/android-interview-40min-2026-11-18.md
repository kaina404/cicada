# Android 技术面试 40 分钟全流程测试（2026-11-18）

对象：讲题卡片（walkthrough cards，`7fa62bd` / `881bb22`），英文教练模式，DeepSeek Flash 出卡。仅 Mac：M4 Pro，dev 版 `com.wquguru.cicada.dev`。

## 1. 目的

之前的用例（[android-interview-full-test-cases-2026-11-17.md](android-interview-full-test-cases-2026-11-17.md)）每个场景都是一场新会议、几分钟、只有一道系统设计题。真实面试是一场会议连续 40–90 分钟、话题来回切：自我介绍 → 简历 → 八股 → 写代码 → 系统设计 → 反问。本测试只开**一场会议、不重置**，按真实语速跑完 40 分钟，看：

1. **话题偏移**：卡片是否始终回答面试官最新的问题，有没有被上一段话题拖住（简历内容串进八股、SSE 解析代码串进系统设计）。
2. **题目切换**：`problems` 是否在换题时增加；显式换题（“let's move on / switch gears / a new problem”）和隐式换题（直接问下一个问题）都要覆盖。
3. **一致性**：系统设计中先定的范围（语音、图片延后）、先提的事件格式（seq），后面的回答是否沿用。
4. **真实性**：简历题只用资料里的硬事实（公司、职责、数字），不把 Debon 的事实挪到 KKday。
5. **时延随会议增长的变化**：原文越来越长，首字和出卡耗时是否变慢。
6. **是否卡住**：每句面试官台词后都必须有新卡片（请求数增加、未失败）。

## 2. 剧本：90 分钟计划压缩到 40 分钟

来源：用户提供的“ChatGPT 移动端”90 分钟面试计划。保留每个环节，每段删减问题数。

| 时间（约） | 环节 | 用例 | 题目 |
|---|---|---|---|
| 0–3 | 开场 | O-01、O-02 | 两分钟自我介绍；最近做的 Android |
| 3–10 | 简历深挖 | R-01～R-04 | KKday SSE 行程从服务端到屏幕；自己写的和团队写的；Debon 崩溃率降 90% 最难的崩溃；机型相关 bug |
| 10–16 | Android 基础 | B-01～B-04 | 子协程失败与 SupervisorJob；一次性事件用哪种 Flow；repeatOnLifecycle；进程被杀后恢复 |
| 16–23 | 现场写代码 | C-01～C-04 | `Flow<String>` 的 SSE 分块拼成完整事件；怎么测；结尾没有换行 |
| 23–37 | 系统设计 | D-01～D-17 | ChatGPT Android 端：澄清范围、分层、单一数据源、协议选型、事件格式、50 token/s 节流、流式 Markdown、Stop、断网、进程被杀、重复发送、2000 个会话同步、语音打断、来电、10 MB 图片、线上指标、两周取舍 |
| 37–40 | 反问 | Q-01 | 候选人提问 |

换题方式有意混用：B-01（“let's move on”）、C-01（“switch gears”）、D-01（“a new problem”）是显式；O-02→R-01、R-04 之后各题内部是隐式。D-02 由面试官把语音、图片延后，D-13 再“捡回来”，用来测范围一致性。

剧本文件：[tools/interview-40min.json](../../tools/interview-40min.json)，每条用例的判据写在 `judge` 里。

## 3. 方法

```bash
scripts/build.sh && open build/Cicada.app
PACE=1 SCENARIOS=interview-40min.json python3 -I -u tools/mock-interviewer.py
```

- **注入**：面试官台词 `themSaid`、候选人发言 `meSaid`、白板文字 `coachOCR`，经 `tools/lsctl` 进入 dev 版。跳过 ASR、判停和真实屏幕。
- **按语速播放（`PACE=1`，本次新增）**：面试官台词和候选人发言按约 150 词/分钟等待，整场时长接近真实面试。
- **候选人照卡片念（`me_card`，本次新增）**：读出当前卡片的 SAY，一句一条 `meSaid`；`next: 1` 时再按一次“下一张”并接着念。这模拟“跟读”，也让卡片自己的内容进入整场原文——偏移会在这里累积。
- **候选人照卡片写（`ocr_card`，本次新增）**：把卡片 TYPE 里的代码或画图文字追加到白板 OCR；每个环节开始时白板清空。
- **判卷**：结构检查（`type`、`problems_min`、`adopted_not_contains` 等）+ DeepSeek 判卷（看不到图片；本场没有图片）。
- **每条台词记录**：开始时刻、`first_ms`（首字）、`settle_s`（台词注入到出卡完成）、当时的 `problem` / `problems` / `adopted` / `constraints`。

### 不覆盖

- R 真人双路音频：ASR 听错、两人重叠说话、真实跟读速度。
- V 真实屏幕：Meet 压缩画面、Android Studio 编辑器、画图工具。
- 界面：焦点、共享可见性、换卡动画。
- 每条用例只跑 1 轮，模型输出有随机性，单次 FAIL 不等于必现。

### 前提（本次踩到，已修）

dev 版默认“没人说话 10 分钟自动结束会议”。第一轮注入的台词不算语音，跑到 11 分钟（D-03）时会议被自动结束，之后卡片全部停止，这一轮作废。现在注入的台词也算听到的语音，复测保持默认 `silenceEnd prompt`，30 分钟没有自动结束。

### 4.4 判卷误差

判卷把判据里的每一项当成必须全部出现（D-10 要求同时提 streaming 状态和前台服务、D-12 要求 Paging 3 + 推送 + 冲突规则、D-15 要求本地预览 + 重试 + 文件 id）。每张卡只有 5 句，列全不现实。下次判据改成“至少覆盖其中两点，且没有错误”。反过来，D-01 判卷没发现卡片是空的，R-02 第二轮没发现夸大，这两类要靠人工复核。

## 5. 结论

- **流程上没有偏离**：31 条台词都在 7 秒内出了新卡片，写代码段能接着白板上的代码改，系统设计能沿用前面定的 seq 和范围，最后反问能停止设计。28 分钟内时延没有变慢。
- **内容上有偏移**：简历里的行程规划会串进后面的八股和写代码（P2-3）；系统设计前后说法有一处矛盾（P2-4）；解题记录基本没起作用（P2-4、P2-7）。
- **要先处理的**：P1-1 已修；P1-2 已补资料。
- 只跑了一轮（加第一轮前 11 分钟对照），注入方式不覆盖真实语音、真实白板和界面；不能当作端到端验收。
