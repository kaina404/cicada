# Android 技术面试实时英文讲解助手 — 完整需求文档

- 日期：2026-11-17
- 状态：供实现方案讨论与交接的需求基准；未开始本需求的编码，未完成效果验收。
- 运行平台：Cicada Mac，目标设备 Apple M4 Pro / 48 GB。Android 是面试内容领域，不是本次开发平台。
- 相关材料：[旧方案草稿](walkthrough-coach-plan.md)、[现有教练说明](interview-coach-local.md)、[ActAI Android 验证场景](actai-android-interview-tests.md)。
- 本文汇总本次讨论的产品需求。旧草稿里的类型名、协议、固定阈值、时间线/Beat 结构、固定分期等不构成实现要求；与本文冲突时以本文为准。当前代码与旧说明仍须由实施者核实。

## 1. 产品目标

根据**当前共享白板的内容**和**候选人与面试官之间的问答**，持续引导候选人接下来怎样用完整、自然的英文回答。

助手必须理解讨论如何发展到当前状态，而不只是回答最后一句问题。它应支持逐步解释、边讲边编码、方案调整、临时追问及题目切换。目标是用户能在一场连续技术面试中实际使用，不以单次生成答案或演示跑通作为交付完成。

用户提出的“未来时间线”和 Git 是帮助说明效果的比喻及设计参考，不要求实现时间线界面、真实 Git 仓库或复杂分支管理。实现者可以选择更合理稳定的架构，但必须满足下述可观察行为。

## 2. 用户、场景与范围

### 2.1 角色与输入

- 用户是面试候选人；对方是面试官。早期对话中的“老师/学生”不作为最终角色定义。
- 通常系统音频对应面试官，麦克风对应候选人；输入来源、回声和重叠语音存在不确定性时不能强行猜测身份。
- 面试主要使用英文，助手主讲稿必须为可直接朗读的英文。中文界面与可选辅助不应混入英文正文。
- 候选人可以照读、改述、跳过、自主发挥、操作白板或暂停思考；不要求逐字遵守生成稿。
- 白板泛指用户选定的共享窗口或屏幕：题目、IDE、在线编辑器、代码片段、伪代码、架构图或图文混合内容。没有共享屏幕时也能完整回答口头问题。

### 2.2 覆盖题型

| 题型 | 代表场景 | 必要行为 |
|---|---|---|
| 原理解释 | Bundle、View 事件分发 | 直接回答，再逐步深入机制、例子和边界，不强制写代码 |
| 技术比较 | 框架、并发或状态管理方案比较 | 比较适用条件和取舍，区分讨论备选与正式改方案 |
| 页面/系统设计 | 类似 ChatGPT 的 Android 聊天页面 | 明确必要范围，讲组成、状态、数据流、异常与设计理由 |
| 编码 | 按题目实现页面或模块 | 配套英文与局部代码建议，跟随实际实现进度 |
| 阅读与排障 | 解释现有代码、定位错误 | 依据可见证据解释行为，不声称看到了完整工程 |
| 简历与项目 | “以前是否这样做过？” | 使用用户确认的经历，支持技术追问与自然接回 |

题型可以在同一道题中变化。概念解释转代码举例、代码讨论转原理解释均应保留上下文。不能因为屏幕出现编辑器就判定必须编码。

### 2.3 已确认的使用条件（2026-11-17 用户确认）

- 会议软件是 Google Meet，一场大约 90 分钟。
- 白板可能由面试官共享，也可能由用户自己共享，中途可能切换；面试官也会直接修改白板内容。
- 讲解与编码**轮流进行**：先说一段，再敲一段。敲代码时暂停跟读，敲完再继续。
- 只有一种界面：技术题、简历题都用同一种卡片呈现。简历题就是只有英文讲稿、没有代码的卡片。
- 建议会议开始时选择整块屏幕作为来源，这样共享方切换后不用重新选择。

### 2.4 不默认纳入的范围

- 自动控制编辑器、自动修改用户代码或自动替用户发言；本次由用户实际说话和操作白板。
- Android/iOS 客户端开发、独立面试工作台、复杂 Git 分支可视化。
- 仅凭截图保证代码能编译、测试通过或全工程正确。
- 自动把生成答案写入个人知识库、自动发布或同步外部文档。

## 3. 核心工作闭环

1. 接收双方发言与共享白板证据。
2. 维护当前题目、有效约束、采用方案、实际讲解与实现进度。
3. 判断新信息的意图、可信度与影响范围。
4. 保留仍然有效的指导，只更新受影响的内容。
5. 给出下一小段英文，按需附代码、例子、澄清句或等待提示。
6. 按候选人的真实行为继续，支持人工纠正。

后台可准备后续内容，但不应预先生成整场固定流程。每次新信息都可以改变理解，不代表每次都要改稿或调用完整生成链路。

## 4. 功能需求

### FR-01 问题理解与讲解路线

- 结合原话和画面识别题目目标、明确要求、约束和期望深度。
- 不把画面中未体现的功能擅自加入必答范围；不默认套用 MVVM、RxJava 或 Compose。
- 范围清楚时直接回答；只有影响方案的关键歧义才提供英文澄清句。
- 维护未完成事项及讲解方向；方向可随讨论修改，不是必须全部走完的固定大纲。
- 区分简短定义与需要持续展开的解释，不能把所有概念题排除在动态讲解之外。

### FR-02 可直接说出口的英文

- 主体输出完整描述性英文，不能只给大纲、关键词或代码。
- 默认使用清楚、自然、便于口述的短句，技术名词保持准确。
- 提供当前句/短段及少量后续预览；用户能回看必要内容。具体句数由实现方案确定，不是固定验收数值。
- 包含开场、理由、例子、修改承接、追问回答、回到主线及结束语。
- 英文解释说明代码做什么及为什么，不默认逐个朗读括号和符号；标识符准确保留。
- 音标和可选中文辅助沿用现有能力时，不应破坏代码、正文及跟读。

### FR-03 白板理解与证据边界

- 识别文字、代码及架构图中与当前问题相关的关系；OCR 是手段，不是唯一产品定义。
- 区分题目示例、参考代码、当前实现、备选方案和废弃内容；不确定时保持未确认。
- 保留文件/区域线索、证据时间、原始内容与可信度。代码大小写、运算符和有意义的缩进不能被归一化破坏。
- 滚动、切文件、遮挡、缩放、光标移动和格式化不等同于语义修改。
- 移出可见区域不等于删除。局部截图不代表整个文件，更不代表完整工程。
- 低置信度、半截输入或画面未稳定时不得强行认定实现变化；重要口头要求仍需及时响应。
- 图中箭头或关系看不清时不能编造连接；无画面时正常使用对话上下文。

### FR-04 代码建议与实际进度

- 编码场景提供与当前步骤对应的代码，说明新增、替换、删除的位置和目的；按需给完整小例子，不强制每段固定行数。
- 改动已有代码时优先给必要局部修改，不重复输出整份实现。
- 根据可确认的实际代码调整标识符、接口和解释；用户采用等价实现时不要求照抄。
- 明确区分“建议写”“正在修改”“已观察到实现”“尚不能确认”。生成代码不是完成证据。
- 标识符命中比例、最后一行出现或用户说了一句计划，都不足以证明步骤完成。
- 只有屏幕证据或用户明确确认足够时推进实现状态；局部可见证据不能用于宣称编译成功。

### FR-05 变化影响判断与局部更新

| 变化 | 预期处理 |
|---|---|
| 附和、无关编辑、格式化、滚动 | 通常保留指导 |
| 正常完成当前操作 | 更新实际进度，不无故重写路线 |
| 局部改名或参数变化 | 更新有关代码和讲稿，保留无关部分 |
| 新增/删除需求 | 更新有效约束及受影响的待完成事项 |
| 明确换方案 A → B | 停止推荐 A，重规划依赖 A 的后续代码和解释 |
| 关键实现疑似消失 | 标记证据变化，判断是否删除或可见性变化，不擅自认定退化 |
| 含糊指代 | 能确定则行动；不能确定则给简短英文澄清句 |

- 判断依据是语义影响，不是改动行数。
- 影响检查覆盖代码引用、接口、调用方、状态管理、测试思路和口头解释等相关依赖，不只替换字符串。
- 已经说过的内容不改写；历史生成版本可保留，但过时建议不得继续作为当前指导。

### FR-06 意图、决定与执行分离

- 区分“能否用 B？”、“比较 A 与 B”、“请改为 B”和“我决定采用 B”。试探性问题不自动成为已接受决定。
- 最新明确要求决定目标；白板说明当前可确认实现。两者可以暂时不同。
- 面试官明确要求 A → B 时，即使白板还是 A，也应提供承接英文和迁移步骤。
- 完成前说“I’ll switch…”等计划表达，而不是声称已经完成。
- 观察到的变化与修改理由分开：未讨论的理由可作为建议，不能伪装成已确认历史。
- 当前采用方案、备选方案和已放弃方案均应可区分，避免错误恢复旧建议。

### FR-07 追问、嵌套追问、换题与返回

- 对当前题目的追问优先回答，保留未完成目标及必要上下文。
- 支持追问中的追问；不能因固定只保留一层而丢失恢复所需信息。
- 回答完后按实际意图继续：自然接回、深入新方向、总结等待或切换题目。
- 追问已经覆盖后续内容时跳过重复，不机械恢复旧稿。
- 明确新题建立独立题目状态，旧题可以回查和恢复；恢复时结合最新白板和约束重新判断。
- 简历插问不应永久丢掉技术主线。问题模糊时提供确认话术，不擅自换题。

### FR-08 自由表达与三种进度

分别维护：实际讲解进度、实际白板操作进度、当前会话是否应等待对方。

- 用户改述、跳句、举例或主动提出方案时，根据真实语义更新已覆盖内容。
- 跟读位置仅用于阅读辅助，不能等同于知识点已解释或任务已完成。
- 停顿可能是思考、编码或等待回应，不能只凭静音自动推进。
- 用户口误或低置信度 ASR 不自动变成新方案；重大变更需要上下文支持。
- 提供手动继续、暂停跟随、回看、返回主线、切换题目及纠正理解的能力；控件布局由实现方案决定。
- 用户纠正后旧推断应失效，并防止后台任务再次恢复旧状态。

### FR-09 完整过程记忆与相关历史回查

不能仅使用最近几张截图或几轮问答作为全部上下文，也不要求每次把全场原始材料重新发送给模型。

需求分为三层：

1. **过程证据**：保留可回查的双方问答、重要白板版本和修改依据，时间上可关联；不要求每帧截图或原声永久保存。
2. **当前解题记录**：每次指导都可获得最初仍有效的目标、当前约束、方案与理由、废弃方案与原因、已讲内容、实际实现、未解决问题及当前追问。
3. **当前细节与相关历史**：使用最近原话和画面；当提及早期要求、旧方案或发生矛盾时，按需取回相应原始证据。

- 关键事实记录来源、确认状态、有效性和替代关系。摘要不应把猜测升格为事实。
- 实际发言、生成建议和已执行操作必须分开记录。
- 历史记录不可静默改写；对原识别的纠正通过新记录关联旧记录。
- 有效约束不能因对话变长而被挤出；废弃约束不能与当前约束无区别地拼接。
- 不能只靠递归摘要累计记忆；需要从原始证据校验关键冲突。
- 存储上限、保留周期、删除和跨会话恢复方式由实现方案明确；证据缺失时需说明不确定，不能伪造可追溯性。

### FR-10 借鉴 Git 的版本与变更记录

- 对关键解题状态建立可追溯版本，记录变更内容、原因和证据。
- 支持比较前后状态、回查旧方案以及讨论备选方案。
- 不要求真实 Git、不要求每句发言一个完整快照，也不要求复杂分支树。
- “回到 A”是在当前要求下重新采用 A，不是回滚整场问答或丢掉后续新增约束。
- 文本差异仅辅助识别变化，语义影响仍需判断；版本记录不能替代事实校验。

### FR-11 五项讲解增强能力

1. **范围与深度**：区分概述、原理、源码、应用、排障；按面试官要求深入或压缩。
2. **例子与推演**：提供小例子，解释过程与结果；条件变更时同步调整，不只给抽象定义。
3. **准确性与一致性**：检查与实际代码、前文和平台条件的冲突；区分 View/Compose 等语境，避免过度绝对化，必要时提供修正英文。不确定的版本/API 细节不能当成确定事实。
4. **长度与收尾**：响应 briefly/go deeper 等要求；问题覆盖后总结并等待，不持续无意义扩写。
5. **追问准备**：放在最后一期实现，只有确认不影响主回答延迟时才开启。低优先级准备少量相关解释方向或候选回答；不抢占当前回答资源。真实问题到来后重新验证适用性，不能因相似就直接播放/展示旧答案，也不能把预测当成实际提问。

### FR-12 简历与项目真实性

- 项目经历依据用户确认资料与运行时知识库；现场设计、示例和生成内容不能冒充个人经历。
- 缺少必要个人事实时给出可供用户补充的提示，不杜撰数字、结果或履历。
- 从经历回答接回现场技术题时，区分“过去实际做法”和“这里建议做法”。
- 本功能不自动修改个人知识库；后续有资料回流能力时也需用户确认内容。

## 5. 界面与交互要求

- 集成现有 Mac 面试助手/纪要相关界面，不新建独立产品工作台。
- 主体突出当前英文讲稿，按需显示当前代码建议和简短状态；不把内部推理、版本号或大段大纲塞给用户。
- 正在读且仍正确的句子保持稳定，普通修改在合适边界更新后续内容。
- 明确失效的方案不能继续推荐；应清楚标识更新并给自然承接句。避免突然滚动、频繁闪动或让用户找不到阅读位置。
- 历史生成内容可以回查，但应区别于当前有效指导。
- 代码不参与口语跟读，不因代码词数造成错误阅读进度。
- 用户操作编辑器时，助手不得抢焦点；遵守现有非激活面板及屏幕共享可见性规则。
- 界面中文简短，本地化沿用项目规则；英文界面也必须验证。

## 6. 调度、可靠性与数据边界

- 连续发言和连续打字应合并处理，避免无意义反复取消与重生成。
- 明确的新要求不能被屏幕防抖阻塞；旧画面与新目标可以并存。
- 生成/审查结果关联当前题目、相关对话、白板证据及回答版本；不适用的过期结果不得回写。
- 不能简单采用“任何新 token 就让请求作废”的方式导致一直无法输出；实现方案必须处理事件合并、优先级和持续输入下的可用性。
- 当前回答和关键纠正优先，追问预备和非必要后台任务可取消。
- 模型失败、超时、断网或屏幕不可读时保留有效内容，标记失效/未确认状态，并允许重试或人工继续；不能用旧答案伪装新答案。
- 区分首句耗时、最新有效问题到首句耗时、变化到有效更新耗时；记录重复改稿、错误推进、旧结果覆盖及历史约束遗漏。
- 不承诺未经实测的“1 秒响应”等数字。技术方案需制定可测量目标，并报告中位数、尾部耗时、样本条件及失败率。
- 只处理用户选择的共享来源。云端处理范围、历史截图存储/清除和会议删除行为需明确，不得宣称全部数据仅在本机。
- 不新增原声长期保存要求；密钥和分享 token 继续遵守 0600 文件等项目规则。记录中不得包含密钥。
- 本地记录是复盘与调试证据。**整场对话原文（文字）可以随每次请求发送给云端**，用于回查早期要求和校验摘要（2026-11-17 用户确认）；截图只发送当前画面，历史截图不发送、不长期保存，重要白板版本以 OCR 文字保存在会议目录，随会议一起删除。

## 7. 关键交互示例

### 7.1 纯原理题

面试官要求解释事件分发 → 助手给直接开场与逐步英文解释 → 面试官追问父容器拦截 → 先回答追问 → 更新已覆盖内容 → 继续尚未解释的部分或总结。全过程不要求代码或截图。

### 7.2 A 改 B

已讲 A 且白板部分实现 A → 面试官明确要求 B → 给承接英文和必要替换建议 → 目标为 B、实际仍为 A → 白板逐步修改 → 更新实际进度与后续讲解。A 的历史保留，A 的失效建议停止展示。与 A 无关的有效要求保留。

如果原话只是“Could we use B here?”，应先比较或澄清，不能直接假设决定切换。

### 7.3 cat → dog → 再加一个

白板有 `val cat = 1` → 要求改为 dog → “Okay, I’ll rename it to dog.” 并建议局部修改 → 确认实际白板变化 → “再加一个”若指代不清，先给澄清句。不能自动编造新变量名和值，也不能全局替换所有自然语言中的 cat。

### 7.4 长对话与返回旧方案

最初要求支持离线 → A 改 B → 多轮技术追问 → 再问下一步：仍保留离线要求及当前 B 的实际完成度。若要求恢复 A，应在当前有效约束下恢复适用部分，不丢掉中间新增条件。

### 7.5 自由表达与技术/经历切换

用户没有照读，自己解释了后面一个知识点 → 助手识别语义覆盖并跳过重复 → 面试官问历史项目 → 根据真实资料回答 → 给过渡句接回当前题目仍未完成的部分。

## 8. 验收矩阵

以下为产品验收要求，不限定单元测试框架、覆盖率或内部类型。

| ID | 场景 | 通过条件 |
|---|---|---|
| AC-01 | 无画面解释 Bundle/事件分发 | 完整英文逐步讲解，按需深入，不强制编码 |
| AC-02 | 页面设计转编码再转原理 | 保留题目与进度，切换内容自然，不重开答案 |
| AC-03 | A → B，白板延迟修改 | 区分目标与实际，及时提供修改指导，不声称已完成 |
| AC-04 | 试探性询问 B | 先分析/确认，不擅自将 B 标为采用 |
| AC-05 | 局部重命名 | 相关代码/解释更新，无关路线不重写 |
| AC-06 | 含糊“再加一个” | 有依据才行动，无依据给英文澄清 |
| AC-07 | 滚动、切文件、格式化、遮挡 | 不误判删除、换方案或完成 |
| AC-08 | 部分代码、OCR 错误、等价写法 | 保留不确定或正确适配，不要求照抄、不夸大完成度 |
| AC-09 | 连续追问及追问中的追问 | 当前问题优先，必要时接回，不漏主线、不重复覆盖内容 |
| AC-10 | 多题切换及回到早先题目 | 能回查相关状态，按当前证据恢复，不限于最近一次记忆 |
| AC-11 | 长讨论后问下一步 | 最初仍有效约束保持，废弃方案不再推荐 |
| AC-12 | 回到旧方案 | 保留新约束和真实历史，不整体倒退 |
| AC-13 | 改述、跳句、自主发挥、静音编码 | 语义跟随，不仅靠读稿光标，不因静音误推进 |
| AC-14 | 正在读时普通修改/重大否定 | 普通更新稳定，重大失效有清楚承接，不突然无提示换整稿 |
| AC-15 | 旧请求迟到与快速连续输入 | 不覆盖新方案，不长期饿死有效回答 |
| AC-16 | 原话与摘要冲突 | 能回查依据、修正当前理解，保留来源与不确定性 |
| AC-17 | 简历插问 | 不虚构经历，能适当接回技术问题 |
| AC-18 | 问题已答完、要求简短或深入 | 调整深度，适时收尾等待 |
| AC-19 | 预备追问失效 | 不抢占主任务，不把预备答案直接当成当前正确答案 |
| AC-20 | 网络/模型/屏幕/跟读失败 | 有效稿保留，失效内容明确，能重试或人工接管（只要求最小处理：保留当前卡片、标为失败、提供重试；不要求本机模型兜底） |
| AC-21 | 英文界面、真实编辑器操作 | 不抢焦点、不遮挡关键操作、代码与跟读互不干扰 |

验证应包含可重复的文本事件与屏幕序列、真实模型输出检查、开发版真实音频/屏幕链路以及用户真人连续使用。注入测试、合成音频和截图自查必须如实标注，不能代替真实使用验收。

先覆盖上述完整功能闭环，再根据实际效果调整实现；可分阶段施工，但不能将未完成能力默认为已交付。自动化测试类别、覆盖目标和延迟阈值由下一轮技术设计明确，现阶段不假定用户已批准具体测试数量或覆盖率。

## 9. 交接给实现 AI 的要求

1. 先核查现有 `InterviewCoach`、`InterviewCoachLogic`、`CoachScript`、`CoachReading`、屏幕捕获/OCR、`LingClient`、会话存储、个人知识库和显示界面，区分已有能力与缺口。
2. 遵守当前 AGENTS.md：仅 Mac、既有界面边界、DeepSeek Flash 回答/审查与 Gemma 跟读等规则。不因 Android 面试题而开发其他平台。
3. 提交实现方案，说明状态模型、事件处理、记忆与证据回查、更新影响判断、异步一致性、界面交互、存储生命周期及异常降级。
4. 说明如何避免把建议视作事实、把试探视作决定、把白板可见性变化视作删除，以及如何避免连续事件造成生成饥饿。
5. 技术选型、具体协议、阈值和分期由实现者论证；不要把时间线、Beat、Git、多 Agent 或“每次只看三张图”当作用户指定架构。
6. 用 FR 与 AC 编号映射实施和验证范围，明确未覆盖项，不能用构建通过代替行为验收。
7. 现有规则“屏幕变化只补充上下文、不触发改稿”与本需求存在变化点：在动态讲解场景中，屏幕语义变化需要能够触发影响审查和必要更新；无关变化仍保持稳定。

## 10. 待技术讨论的选择及建议默认值

这些问题不妨碍需求文档完成，不应被误记为用户已确认的偏好。

| 选择 | 建议默认值/边界 |
|---|---|
| 首要白板环境 | 先以清晰的共享代码编辑器验证核心闭环，再覆盖架构图；最终范围包含二者，图示能力未完成必须标注 |
| 推进方式 | 自动理解实际发言与操作，保留手动纠正；不以固定静音时间作为完成条件 |
| 自由表达 | 必须支持，不限定用户照读；显示跟读与语义覆盖分离 |
| 改方案主动程度 | 明确要求即调整目标；试探性问题先比较或确认 |
| 历史存储与回查 | 重要事件与证据可追溯，当前状态有界；具体介质、压缩与保留周期待设计 |
| 屏幕权限和云端视觉能力 | 核实当前可用链路，测量真实识别效果，无法识别时保守降级 |
| 性能与测试 | 先建立可重复基线，再定具体目标；不可跳过关键状态与异步行为验证 |

## 11. 旧草稿中的附加候选（不混入已确认核心范围）

现有旧草稿还出现了模拟面试官彩排、会后复盘/资料回流、自动代码正确性守护和指导画图等建议。处理如下：

- **模拟面试官彩排**可作为可重复验证工具；做成正式用户功能、TTS 交互和入口需另行确定。
- **复盘与知识回流**可复用过程记录，但不自动写入知识库；正式复盘产品功能另议。
- **代码正确性检查**纳入 FR-11 的有证据的一致性检查；仅凭框架关键词自动报错、声称编译验证通过不在授权定义内。
- **架构图理解**属于白板范围；自动编辑绘图工具不在本次范围。按需提供绘图建议可在技术设计中细化。

这些补充不得挤占核心实时指导的可靠性，也不得被误报为本轮已实现功能。
