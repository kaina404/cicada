# 答题路线：真实模拟面试回放（2026-11-07）

素材：`ResumeDoc/AndroidEngineerMockInterview.mp4`，53 分钟英文 Android 移动端系统设计模拟面试（Facebook 信息流：列表页 + 详情页，点赞评论，离线）。

方法：用本机 `SpeechAnalyzer` 转成 616 句带时间戳的文字，人工标出面试官 / 候选人；面试官的话用 `themSaid:`、候选人的话用 `meSaid:` 按原时间（2 倍速）喂给开发版，模型 Gemma 4 E4B。每次路线更新都和候选人接下来真实说的话对照。测试时用 `endTimes:100000,600,600`，否则没有系统声音 11 分钟后会议会因“静默”自动结束（测试假象，不是产品问题）。

## 发现并修好的问题

| 问题 | 现象 | 修法 |
|---|---|---|
| 连续对话时路线不更新 | 每来一句就把更新往后推 5 秒，或打断正在生成的请求；开场 2 分钟一次都没出 | 已有等待中的更新就不再推后；正在生成时只记一笔，生成完再补一次 |
| 题目没被识别 | 面试官用陈述句出题（“So we need to design an app that has 2 screens.”），路线却被开场的“ready to start our system design mock interview?”占了 | 识别 “need to / let's / you'll design…” 这类出题陈述；一步都没讲到的路线可以被新题替换 |
| 步骤重复 | 模型用步骤名代替编号回答 Now:，同一步被插进三次 | 名字和已有步骤相同时跳到那一步 |
| 路线骨架不像移动端面试 | 后端式的“范围 → 架构 → 数据模型 → 瓶颈”，候选人讲 API 和客户端分层时卡在“数据模型”8 分钟 | 出题时给出移动端顺序：需求范围、API 契约、高层设计、客户端架构、本地存储与离线、深挖 |
| 提示空泛 | 62% 的“接下来”是“We need to decide X”“I'll detail X” | 要求说出内容本身（字段、选择加理由、步骤），给出两个例句，点名禁止宣告句；整场回放降到 15% |
| 面试结束还在提示 | “Let's wrap up” 之后继续出路线；面试官点评里的“high-level design … how do they play together?”又开了一条新路线 | 对方收尾时结束路线，本场之后不再自动开（换话题或手动“按此规划”仍可以） |

## 修好后的表现（第 3–6 轮）

- 路线从真正的题目生成：需求与范围 → API 契约 → 高层设计 → 客户端结构 → 缓存与离线同步，和候选人实际顺序一致。
- 提示与候选人随后真实回答吻合的例子：分页游标加 before/after（10:07，候选人 9:39 起讲）；Coroutines 优于 RxJava（28:41）；Room + 内存两级缓存（29:51 / 31:19，候选人 30:40 起讲）；一个库多张表（36:01）；乐观更新（39:05）；单独的用户互动仓库（40:49）；指数退避重试（43:25，候选人 43:26）；Compose Navigation 传 post ID（46:21）；从一开始就分模块（48:13）。
- 提示词调法：开发版临时把每次路线请求存成文件（回放 23–50 分钟收集 119 份），再离线换 `<task>` 重发对比，一版几分钟。说明“只开了头不算讲完”的版本打勾反而更多，没有采用。
- 仍不理想：步骤有时打勾偏早（刚进入客户端架构就跳到离线）；不少提示落后半拍，复述候选人刚讲过的内容；约 15% 仍是过渡句。

## 实际播放复测（同日，VLC 播放视频，开发版只听电脑声音，读屏选中 VLC 窗口）

只放了前 5.5 分钟（开场与需求澄清）。不再手动标双方，靠声纹和措辞判断。

| 问题 | 现象 | 修法 |
|---|---|---|
| 声纹未定前措辞猜错 | 前约 100 秒一半判反，面试官讲题被当成我方，第 45 秒「需求与范围」被打勾，之后 4 分钟提示一直讲 API | 说话人识别开着而声纹未定时，这些行在路线里标 `Unsure:`，不触发更新、不算我方 |
| 更新太频繁 | 320 秒 27 次，14/26 次结论不变；首字从 1.2 秒涨到 3.5 秒 | 我方停顿 2 秒、说满 150 字、交还发言或对方提问才更新；路线请求不再带 300 秒原文（单声道里全标 `Them:`），只带读屏、纪要和问题以来的发言 |
| 需求阶段被模型提前跳过 | 我方一说出一条需求就被判为讲完 | 第一步是需求时由代码保持，直到我方说「covers / move on / API / architecture」等；提示从固定澄清清单里取尚未提到的下一问（规模、内容类型、无限列表、发布、实时、离线、地域、延迟） |
| 提示词示例泄题 | 两个示例正出自本视频（Post 字段、游标 before/after） | 换成聊天应用的例子；更新回复不再要 `Q:` 行，宣告句黑名单加 I suggest / I propose / Next |
| 其他 | 慢的路线请求让下一次回答丢截图；我方已回答的问题仍出卡片 | 只有带图请求超过 2 秒才省图；我方确认的 6 词以上发言取消排队中的回答 |

离线重放同一段（按新规则模拟时机，本机 Gemma 4 E4B）：模型调用 27 → 5，其余 22 次由代码给出下一问；需求步骤保持到 289 秒候选人说「covers … functional requirement」；建议的下一问依次与候选人随后真实问的吻合（无限列表 135 秒、发布 173 秒、实时 185 秒、地域 234 秒、离线 251 秒、延迟 313 秒）。重放的停顿由逐行时间近似，不等于应用内实测；后 48 分钟（API、客户端架构、离线）尚未用新规则复测。
