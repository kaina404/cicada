# 讲题模式 P0：DeepSeek 读白板与带全文延迟

2026-11-17。对应 [技术方案](../walkthrough-coach-plan.md) P0、[需求](../android-technical-interview-assistant-requirements.md) FR-03 / FR-09 / §6。只是直接调用接口的探针，没有接入 App，也没有经过 ASR、判停和界面。

## 材料

- 画面：`AndroidEngineerMockInterview.mp4`（53 分钟，1080p）。这是一场公开的**移动端系统设计**模拟面试（Facebook News Feed），候选人在 Chrome 里共享 Excalidraw，Google Meet 的视频小窗浮在白板右下方。录像是候选人本机的画面，**不是**对方经 Meet 收到的压缩画面。
- 标准答案：同一个 Excalidraw 房间的最终状态（只读，112 个元素，其中 47 段文字），以及用户导出的 SVG。最终状态里有几段文字是录像之后才改的，所以逐帧对照时以画面为准，人工核对。
- 模型：`deepseek-flash`，关闭 thinking，`temperature 0`，和 App 的 `CoachDeepSeekTest.body` 一致。
- 脚本：`tools/whiteboard-probe/`（`probe.py read|pairs|latency`、`known.py`）。

## 结果

### 1. 读文字：可用

| 项 | 结果 |
|---|---|
| 10 张关键帧（需求、API、高层架构、分层架构 70–110% 缩放、评分反馈） | 9 张输出合法 JSON；文字基本逐字正确，包括原文的拼写错误 |
| 遮挡 | 严格提示词下，被小窗或屏幕边缘挡住的字写成 `userIn…ion` 并列进 `occluded`，**不补全**。宽松提示词下，模型曾自行补成 `userInteraction` |
| 失败 1 张（180 秒） | 线框图里重复的 `Text, Text, Text` 让输出陷入循环，写满 1,500 token 后 JSON 解析失败 |
| 噪声 | 偶尔混入协作者名牌、缩放比例、Meet 小窗上的人名 |
| 一张图的 token | 固定约 970 个，与分辨率无关（服务端会缩小图片） |
| 首字 | 0.61–1.30 秒（10 次） |

### 2. 箭头连线：不可靠

2760 秒那帧（分层架构，70% 缩放）列出 8 条连线，只有 `PostRepository → PostLocalDataSource` 等 2 条和标准答案一致，其余是编的。框里的文字都对，连线关系错得多。

### 3. 变化判断：要靠本机过滤

8 对相隔 20 秒的画面，人工标注后核对：

| 对（秒） | 实际 | 模型 | 判定 |
|---|---|---|---|
| 300 | 微小平移；加了 “1.”；改了一个拼写 | 加了 “1.” | 基本对，漏了拼写修改 |
| 700 | 正在写一条新 API | 新增，标为正在写 | 对 |
| 1100 | 平移；可能新增一行 Authorization | 平移，但把露出来的整段 API 列成新增（14 条） | **错** |
| 1250 | 新增 CDN 框和箭头；临时的 LoadB 框没了 | 一致 | 对 |
| 1500 | 平移；新增 Domain/Usecase 层 | 一致 | 对 |
| 1800 | 缩小 + 平移；正在写新框 | 缩放；正在写新框 | 对 |
| 2200 | 平移，没有变化 | 平移；把名牌挡住的框说成“编辑” | 基本对，有一个假阳性 |
| 2600 | 平移；新增 Exponential Backoff | 平移；另外把露出来的 BE、SSOT 列成新增 | 部分错 |

- 原始准确：完全对 5/8。错误都是同一类：**平移后露出来的旧内容被当成新增**。
- 把之前见过的白板文字作为“日志”放进请求：**没用**，1100 秒那对仍列出 14 条。
- **由程序把模型说的“新增”和之前读到的文字做模糊比对**（归一化后相似度 > 0.85 或包含）：1100 秒剩 1 条（Authorization，很可能确实是新写的），2600 秒只剩 `Exponential Backoff + Retries`，两对都变成正确。

### 4. 带整场原文的延迟：达标

模拟 90 分钟双方原文（约 2.85 万 token），每种情况 6 次，同一网络：

| 情况 | 首字中位数 | 缓存命中后中位数 | 最慢 | 缓存 |
|---|---|---|---|---|
| 纯文字 | 0.67 秒 | 0.66 秒 | 1.25 秒（第一次，无缓存） | 第 2 次起命中 28,288 / 28,480 |
| 文字 + 1 张图 | 0.67 秒 | 0.63 秒 | 1.53 秒（第一次） | 第 2 次起命中 29,184 / 29,449 |

样本少（每种 6 次）、只有一种网络条件，只能说明量级。测试里每次的图片相同，所以图片也被缓存了；实际上图片每次都变，**图片要放在请求最后**，才不会破坏前面原文的缓存。

## 对方案的影响

1. **截图方案成立**，不需要先做本机 OCR 才能读文字。
2. **新增判断由程序做**：模型负责读出当前画面的文字，程序拿它和日志里已有的文字比对，决定什么是新的。日志的作用是给程序比对用，不能指望模型自己去对照。这一条要写进方案第二节。
3. **连线不能当事实**：箭头关系只作 `unconfirmed` 参考。需要准确连线时，结合讲解原文（候选人会说 “the repository talks to the local data source”）。
4. **限制输出**：读图请求要设 token 上限，并要求重复内容合并（“3× Text, Text, Text”），避免 180 秒那种循环。
5. **请求顺序**：规则 → 资料 → 原文 → 记录 → 图片放最后。
6. **题型**：这场真实面试是画图为主的系统设计，几乎没有代码。方案里的「先说后写」对这种题应该是「先说后画」，`TYPE` 也要能描述“画一个框、连一条线”。

## 没有覆盖的

- **对方经 Meet 共享、我方收到的压缩画面**：这次是候选人本机画面，最关键的差异没有测到。需要一段面试官共享屏幕的真实录像或截图。
- 代码编辑器画面（这场面试没有写代码）。
- 首句（不只是首字）延迟、ASR 和判停在内的端到端延迟。
- 多次重复时的波动、不同网络条件。
