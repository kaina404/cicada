# 讲题模式（Walkthrough）技术方案

2026-11-17。仅 Mac。

**状态：技术方案，未实现、未验收。** 需求基准是 [android-technical-interview-assistant-requirements.md](android-technical-interview-assistant-requirements.md)（下称「需求」），本文按其中的 FR / AC 编号逐条对应。协议字段和阈值都是实现候选，P0 实测后再定。此前本文里的「产品目标与响应策略」一节已经并入需求的 FR-05 / FR-06 / §7，这里不再重复。

**一句话**：每次有新证据，就把「整场原文 + 解题记录 + 刚刚的变化 + 当前白板」交给 DeepSeek，只要求它给出**下一张卡片**，并顺带更新解题记录。

## 一、请求组成

前面稳定、后面多变，方便命中 DeepSeek 上下文缓存：

| 顺序 | 内容 | 对应需求 |
|---|---|---|
| 1 | 规则：现有回答规则 + 卡片协议 + 需求里的行为规则（试探和决定分开、目标和实现分开、不编造、观察和理由分开、项目经历真实） | FR-02/05/06/12 |
| 2 | 资料 `knowledge/`，整份、固定 | FR-12 |
| 3 | **整场原文**：双方全部最终转写，带时间和行 ID，只追加 | FR-09 第 1、3 层 |
| 4 | **解题记录**（见第二节）：所有题目的状态 + 追问栈 | FR-01/06/07/09 第 2 层 |
| 5 | **事件日志**中当前题目的部分 | FR-10 |
| 6 | **变化**：上一个已确认版本之后的新原文、白板 OCR 增删 | FR-05/10 |
| 7 | 当前卡片 + 用户在它之后实际说过的话（`committed`） | FR-08 |
| 8 | 白板现状：最新截图 + OCR；有变化时再附上一张，用来区分滚动和修改。**图片放最后**，每次都变的图片才不会破坏前面原文的缓存（P0） | FR-03 |

- 整场原文可以回查，所以不需要“什么时候去取旧证据”的机制；摘要和原话冲突时，以原话为准（AC-16）。
- 90 分钟的原文大约两三万 token，只追加，所以缓存几乎每次都能命中。P0 实测带全文请求的首句延迟。

## 二、解题记录与事件日志（`CoachCase.swift`，纯逻辑，可单测）

### 2.1 解题记录（当前状态，有界）

```swift
struct CoachCase: Equatable {
    var problems: [Problem]          // 全场题目，可回查、可恢复
    var current: Int                 // 当前题目
    var asides: [Aside]              // 追问栈，支持追问里的追问
}
struct Problem: Equatable {
    var id: String
    var goal: String                 // 题目目标
    var constraints: [Fact]          // 有效约束
    var adopted: String              // 采用方案
    var alternatives: [String]       // 讨论过的备选
    var abandoned: [Fact]            // 已放弃的方案及原因
    var spoken: [String]             // 已讲到的点（来自用户实际发言）
    var implemented: [Fact]          // 白板上能确认的实现
    var pending: [String]            // 待办
}
struct Fact: Equatable {
    var text: String
    var source: Source               // interviewer | candidate | board
    var status: Status               // confirmed | unconfirmed | superseded
    var evidence: [String]           // 原文行 ID 或白板版本 ID
}
struct Aside: Equatable { var question: String; var returnTo: String }
```

- **试探和决定分开**（FR-06）：“Could we use B?” 只进 `alternatives`；“Let's switch to B” 才改 `adopted`，A 进 `abandoned`。
- **目标和实现分开**（FR-06）：`adopted` 是 B，`implemented` 仍可以是 A，两者暂时不同。
- **回到 A**（FR-10 / AC-12）：A 从 `abandoned` 回到 `adopted`，`constraints` 原样保留，不倒退。
- **追问栈**（FR-07）：追问入栈，答完出栈；栈顶的 `returnTo` 决定怎么接回。追问已经覆盖的点会写进 `spoken`，接回时不重复。

### 2.2 事件日志（借 git：只追加，不改写）

- 每条：时间、来源、题目 ID、一句事实、证据 ID。方案作废就新加一条“A 已作废”，旧条目不动；纠正识别错误时，加一条关联到旧条目（FR-09/10）。
- **模型每次响应顺带输出解题记录的修改**（`CASE:` 一行操作列表），不多一次调用；日志条目由程序根据实际生效的修改生成。程序校验：缺证据的事实只能标 `unconfirmed`；没有双方原话作证据的 `adopt` 只算备选；`spoken` 只认候选人自己的原话。
- **变化的比较基准是上一个已确认的版本**，而不是上一次请求。请求被取消时，这次的变化会留到下一次请求里，不会丢。
- **新增由程序判断，不由模型判断**（P0 实测）：模型负责读出当前画面的文字；程序拿它和日志里已见过的白板文字做模糊比对，只有没见过的才算新增。把日志直接交给模型没用，平移后露出来的旧内容仍会被列成新增。
- **连线只作参考**（P0 实测）：模型读框里的文字很准，箭头连线多数是编的，一律标 `unconfirmed`，需要时结合讲解原文判断。
- 全部写进会议目录的 `coach.jsonl`。

## 三、卡片协议（流式；「说」排在最前）

~~~
<<<CICADA_CARD>>>
HEARD: rename cat to dog                  ← 可选：据以行动的面试官指令
FIX: Actually, let me use dog here.       ← 可选：正在念的句子已经不对时的纠正句
SAY:
OK, I'll rename it to dog.
TYPE: replace at="val cat"                ← 可选：add / replace / delete 及位置
```kotlin
val dog = 1
```
THEN: Next, I'll add the retry logic.
REASON: (optional) ...                    ← 可选：对话里没出现过的理由，只作建议
CASE: [{"op":"adopt","text":"val dog = 1","evidence":["L42"]}]   ← 解题记录的修改；日志由程序从这些修改生成
~~~

- 画图白板的系统设计题（P0 录像就是这种）：`TYPE` 也可以是“画一个框 / 连一条线 / 写一段文字”，说明放在哪里；「先说后写」对这种题就是「先说后画」。
- 没有新证据时输出 `KEEP`，卡片不动（FR-05）。
- “再加一个”指代不清时，`SAY` 是一句英文澄清，不出 `TYPE`（AC-06）。
- 计划用 “I'll switch…” 这种说法，不说已经完成（FR-06）。
- 白板代码有能确认的明显错误时，下一张卡片先给自我修正（FR-11 第 3 条）。

## 四、卡片的两个阶段与进度

需求要求分别维护三种进度（FR-08）：讲解进度（`spoken`）、白板进度（`implemented`）、是否该等对方。

| 阶段 | 显示 | 跟读 | 什么时候检查 |
|---|---|---|---|
| 说 | `SAY`，跟读高亮 + 音标 | 开 | 跟读光标到末尾；或用户说完一句话（合并、限速） |
| 写 | `TYPE` 代码卡 | 暂停 | 白板稳定 3 秒且出现了大部分标识符；或手动 |

- **上面这些只是“该检查一下了”的信号，不是完成证据**（FR-04/08）。是否讲到、是否写好，由模型对照 `committed` 和截图判断，结果写进 `spoken` / `implemented`。
- 静音不推进（AC-13）。问题答完时，`SAY` 是简短收尾，`THEN` 是“等待对方”（AC-18）。
- 手动：`⌃⌥→` 下一张、`⌃⌥A` 重新生成、暂停跟随、回到主线（FR-08）。用户纠正后，旧推断作废，后台结果不能把它恢复回来（FR-08 最后一条）。

## 五、调度：避免作废太多导致一直出不了回答

| 优先级 | 触发 | 对正在跑的请求 |
|---|---|---|
| 1 | 面试官说完一句完整的话（判停后） | **作废并重跑** |
| 2 | 手动 | 作废并重跑 |
| 3 | 卡片检查信号（第四节） | 不作废；排队 |
| 4 | 白板变化：画面稳定 2 秒且 OCR 变化明显；至少间隔 5 秒 | 不作废；排队 |

- 只有优先级 1、2 会作废请求。用户说话、敲代码时，结果照常发布，再用最新状态排一次检查。这样持续输入时也能出回答（需求 §6、AC-15）。
- 明确的新要求不等屏幕防抖（需求 §6）。
- 同一时间只跑一个请求，排队的信号合并成一次。
- 发布时的当前句规则：已说的不改；当前句仍然正确，就从下一句开始换；已经不对，就显示 `FIX`（AC-14）。

## 六、白板

- 推荐会议开始时选整块屏幕；笔记窗口是 `sharingType = .none`，需要实测确认不会出现在截图里。
- Meet 收到的共享画面是压缩视频，字可能糊；看不清就标 `unconfirmed`（FR-03）。
- 滚动、切文件、格式化、遮挡不算修改，由模型结合前后两张图判断；移出画面不等于删除（FR-03 / AC-07）。
- 画图工具的截图直接给模型看，看不清的箭头不编造（FR-03）。
- 会议结束时，截图照现有规则清除；重要白板版本只保存 OCR 文字（需求 §6）。

## 七、界面（`CandidateFeed`，笔记窗口和浮动助手窗口共用）

自上而下：题目目标和“接下来”一行（小字） → `HEARD`（灰色） → `FIX`（强调色细边框） → `SAY`（主区域） → `TYPE` 代码卡 → `THEN`（灰色） → `REASON`（灰色小字，不跟读） → 可折叠的「之前的卡片」（灰色，和当前卡片明确区分）。

- 换卡时淡入淡出，不突然滚动（需求 §5）。
- 代码不参与跟读：`CoachScript.words()` 跳过代码块（需求 §5）。
- 不抢焦点，遵守非激活面板和屏幕共享可见性规则（AC-21）。
- 文案用中文作为 key，跑 `python3 scripts/strings.py --write`，补齐 en/ja/ko，检查英文界面。

## 十一、风险

- **DeepSeek 读 Meet 截图的准确度、带整场原文的延迟**：都没验证过，所以排在 P0。
- **模型给的 `CASE` 补丁出错**：程序校验格式和证据；整场原文一起发，下一次请求可以纠正。
- **面试官改白板时，判断不了是谁改的**：只按对话和时间判断，判断不了就只记“白板变了”。
- **ASR 听错标识符**：显示 `HEARD` 让用户核对；名字优先和白板上已有的写法一致；拿不准就给确认句。
- **真人验收**：真人跟读、真实 Meet 白板、面试官多人重叠说话都需要人来测；模拟面试官不能替代真人。
